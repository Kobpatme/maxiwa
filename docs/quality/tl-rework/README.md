# ผลตรวจแก้โฟลว์งานตีกลับ TL

วันที่: 29 ตุลาคม 2026

โฟลว์เป้าหมาย: User ส่งกลับแก้ไข → TL รับงานใหม่ → แก้ข้อมูล/แนบหลักฐาน → ส่งตรวจรับใหม่ → User ตรวจรับ → แนบหลักฐานคืนเงินและปิดงาน

## การเปลี่ยนแปลง

- ปุ่มดำเนินการ TL อิงสถานะงาน แสดงได้แม้มีหลักฐานจากรอบเดิม ทั้งหน้าต่าง TL และหน้ารายละเอียด
- เก็บหลักฐานเดิมและเพิ่มหลักฐานรอบแก้ไข โดย User เห็นลิงก์แยกทุกไฟล์
- ยกเลิกการเปลี่ยน `tl` เป็น `ret` อัตโนมัติจากการพบไฟล์เก่า
- การบันทึกข้อมูลเบื้องต้นและแนบเอกสารเพิ่มเติมไม่ส่งงานไปตรวจรับ
- เหตุผลตีกลับยังแสดงหลังรับงานใหม่ และประวัติระบุการส่งงานแก้ไขให้ตรวจรับใหม่
- อัปเดต `status` และ `status_final` พร้อมกันในขั้นตีกลับ/รับงาน/ส่งตรวจรับ และเริ่มตรวจรับที่ `return_status = Pending`
- ป้องกันฟอร์มขั้นปิดงานเขียน `return_status` เก่าทับผลตรวจรับของ User
- บันทึกประวัติลงสำเนาข้อมูลก่อน เมื่อการบันทึกล้มเหลวไม่เพิ่มประวัติสำเร็จในข้อมูลหน้าจอ และปิดหน้ารออัปโหลดเสมอ
- แก้การอ่านบทบาทในหน้ารายละเอียดให้ใช้ `CURRENT_USER` ตัวเดียวกับระบบล็อกอิน
- เวลา TL ใช้รอบรับงานล่าสุด แทนรอบแรกที่ปิดไปแล้ว
- โหมด local fixture รองรับการรับงาน แก้ไขรายการเดิม และแนบไฟล์จำลองโดยไม่เรียกเขียน Firebase

## วิธีทดสอบ

`npm test` รันชุดเดิมและ `scripts/tl-rework.test.mjs` รวมทดสอบ Node 11 รายการ (workflow 9 และ auth migration 2) รวมทั้ง domain/baseline checks

ชุด workflow ใช้ฟังก์ชันจาก `index.html` โดยตรงใน VM และจำลองช่องกรอก/ตัวบันทึกข้อมูล ครอบคลุม:

1. ตีกลับและส่งตรวจรับซ้ำสองรอบ พร้อมเก็บไฟล์เดิม
2. งานปกติบังคับหลักฐานก่อนส่งครั้งแรก
3. ฝ่ายอาคารส่งตรวจรับได้โดยไม่บังคับไฟล์ TL
4. ส่งรอบแก้ไขโดยใช้หลักฐานเดิมเมื่อแก้เฉพาะข้อมูล
5. แนบเอกสารเพิ่มเติมแล้วสถานะเดิมยังอยู่
6. ไม่ส่งซ้ำจากสถานะตรวจรับ ปิดงาน หรือยกเลิก
7. การบันทึกล้มเหลวในขั้นตีกลับ รับงาน บันทึกข้อมูล และส่งตรวจรับ
8. ยกเลิกเหตุผลตีกลับหรือส่งกลับซ้ำไม่เปลี่ยนงาน
9. การนับระยะเวลา TL ของรอบล่าสุด

ชุด `scripts/tl-rework.browser.mjs` ใช้ Microsoft Edge แบบ headless คลิกหน้าจอจริงของบัญชี User และ TL ใน local fixture สองหน้า และส่งสำเนาข้อมูลจำลองระหว่างหน้าตามจุดส่งมอบงาน ครอบคลุม:

- ตีกลับ → รับใหม่ → แก้ข้อมูล → ส่งตรวจรับ ซ้ำสองรอบ
- บันทึกฟอร์มหลักระหว่างรอ TL แล้วไม่ข้ามขั้น
- User ตรวจรับ → แนบไฟล์ปิดงาน → `done` พร้อม `return_status = Done`
- ส่งงานปกติครั้งแรกและตรวจหลักฐานบังคับ
- แนบเอกสารเพิ่มเติมแล้วสถานะไม่เปลี่ยน
- กู้เส้นทางของรายการเก่าที่ค้าง `On Process` พร้อมไฟล์เดิม โดยส่งจากหน้ารายละเอียดได้
- ตรวจว่าไม่มี uncaught browser errors และหน้ารออัปโหลดไม่ค้าง

ผล browser เก็บใน [browser-results.json](browser-results.json) พร้อมภาพหน้าจอในโฟลเดอร์นี้

รันซ้ำโดยเปิด `tools/local-server.mjs` ด้วย `DEPOSIT_TEST_PORT=4175` แล้วรัน `node scripts/tl-rework.browser.mjs` (ติดตั้ง Playwright หรือกำหนด `DEPOSIT_PLAYWRIGHT_PATH`; กำหนด `DEPOSIT_BROWSER_PATH` เมื่อต้องการใช้ Edge ที่ติดตั้งในเครื่อง)

## ขอบเขตการยืนยัน

การทดสอบ browser ใช้ข้อมูลและไฟล์สังเคราะห์บน local server; Firebase SDK initialization และ Chart.js ใช้ shim เพื่อให้รัน offline ส่วนโค้ดหน้าจอ ตัวจัดการปุ่ม การตรวจไฟล์ และการเปลี่ยนสถานะเป็นโค้ดจริงของแอป โหมด fixture ไม่ยืนยันการจัดเก็บถาวรหรือการทำงานข้ามผู้ใช้ผ่าน Firebase จริง

ตรวจการเรียก `updateDeposit()` แล้วพบว่า adapter ส่ง patch ไป Firestore โดยตรง ไม่มีตัวแปลงสถานะอื่น ส่วน `firestore.rules` ใน repository เป็นชุดเตรียม Auth migration ตาม `docs/auth-security-migration.md`: allowlist และ version/audit contract ยังไม่ครอบคลุม payload ของโฟลว์ปัจจุบัน เช่น `log`, `status_final`, `tl_accept_date`, วันที่ดำเนินการ และการตีกลับโดย owner งานนี้ไม่ได้แก้หรือ deploy ชุด Rules ดังกล่าว และไม่ได้เปิด Firebase Auth mode

ยังไม่ได้ทดสอบ Firebase/Storage ที่ใช้งานจริง หรือ deploy ระบบ production ไม่ได้นำผล local ไปอ้างว่า integration กับ Rules จริงผ่านแล้ว
